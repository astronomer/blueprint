# DAG Post-Processing

The `on_dag_built` callback: applying settings that are not authoring decisions at all.

## Why you'd do this

DAG args templates cover the settings authors choose from. Some settings are not theirs to
choose — provenance tags, generated documentation, access control lists, lineage registration,
an inventory pushed to a catalogue. Putting those in a config model would invite a value where
you want a rule.

`on_dag_built` runs once per DAG, after every step is wired up. Two things make it able to do
what a template cannot: it receives the finished DAG object, so it can inspect what was
actually built, and it receives the path the DAG came from, which `render()` never sees.

## Files

| File | What it does |
|---|---|
| `dags/loader.py` | The callback: provenance, directory-derived ownership, generated docs |
| `dags/payments/ledger.dag.yaml` | Three steps, no ownership fields at all |
| `dags/growth/signups.dag.yaml` | Same shape, different directory, different owner |
| `dags/blueprints.py` | Ordinary extract/load — not the point of this example |

Note there is no `dag_args.py` here. These DAGs set only `dag_id`, `schedule`, `description` and
`steps` — the fields the built-in `DefaultDagArgs` allows. Everything else is applied afterwards.

## Run it

```bash
../run.sh dag-post-processing
```

## Walk-through

### The hook

```python
def apply_platform_policy(dag: DAG, config_path: Path) -> None:
    team = config_path.parent.name
    source = config_path.name.removesuffix(".dag.yaml")

    dag.tags = [*(dag.tags or []), f"team:{team}", f"source:{source}"]

    for task in dag.tasks:
        task.owner = team

    task_ids = sorted(dag.task_ids)
    dag.doc_md = (
        f"Generated by Blueprint from `{config_path.name}`.\n\n"
        f"Owner: **{team}**. Raise issues with that team.\n\n"
        f"Tasks ({len(task_ids)}): {', '.join(f'`{t}`' for t in task_ids)}\n"
    )


build_all_airflow_dags(on_dag_built=apply_platform_policy)
```

That is the whole wiring: one keyword argument. The callback returns nothing and mutates the DAG
in place.

### Ownership from the directory

`team` comes from `config_path.parent.name`. Neither YAML file mentions a team, and neither has
to: in a repository where each team owns a directory, the location already carries that fact,
and repeating it in every file is a chance to get it wrong.

A `BlueprintDagArgs` template cannot do this. `render()` receives the validated config and
nothing else — no path, no filename. If policy depends on *where* a file is, it belongs here.

### Rewriting what was already built

```python
for task in dag.tasks:
    task.owner = team
```

The tasks exist by the time the callback runs, so their attributes can be set directly. Passing
`owner` through `default_args` would have required knowing the team before the tasks were built —
which is exactly what this example does not know.

The same applies to anything derived from structure rather than declaration. The generated
`doc_md` lists the tasks the DAG actually ended up with:

```
Tasks (3): `extract_refunds`, `extract_transactions`, `load_ledger`
```

`payments_ledger` reports three tasks and `growth_signups` two, and nothing computed that count
in advance. A blueprint whose `render()` returns a config-dependent number of tasks is counted
correctly here for the same reason.

### Side effects

```python
log.info("dag_inventory dag_id=%s team=%s source=%s tasks=%d", ...)
```

The callback is also where an out-of-band write goes: registering the DAG in a catalogue,
publishing lineage, recording an inventory row. The DAG is complete at this point, so what you
record describes what was built rather than what was requested.

Keep it cheap. This runs on every DAG parse — every 30 seconds or so, for every file — so a
network call here is a network call in the DAG processor's hot loop.

Keep it non-fatal too, and note how sharp the edge is. The per-file error handling in
`build_all_airflow_dags` catches `BlueprintError`, Pydantic's `ValidationError` and
`yaml.YAMLError`. Anything else your callback raises — a `KeyError`, a timeout from that
catalogue call — escapes it and propagates out of the loader, so **no** DAG in the project is
registered, not even the ones already built:

| Callback raises | `skip_invalid_dags=False` | `skip_invalid_dags=True` |
|---|---|---|
| `BlueprintError` | whole load fails | that file is skipped, the rest build |
| anything else | whole load fails | whole load fails |

So `skip_invalid_dags` is not a safety net here. If the callback does anything that can fail,
wrap it yourself and log rather than raise — one unreachable catalogue should not empty your
Airflow instance.

### What belongs here rather than in a template

Ask whether a DAG author would ever legitimately want it different.

- **Yes, within limits** → a config field on a DAG args template, constrained. See
  [dag-arguments](../dag-arguments/).
- **No, but it is still an authoring-shaped setting** → `render()` on the template,
  unconditionally.
- **Not their concern at all, or derived from the file's location or contents** → here.

Provenance tags, access control and catalogue registration are platform bookkeeping. A DAG
author has no opinion about them and should not be offered one.

## What to look at in the UI

Both DAGs are tagged `team:…` and `source:…`, and neither YAML file contains the word `team` or
any tag.

Open either DAG → **Docs**: the generated panel, listing the tasks that DAG actually has.

Open any task → **Details**: `Owner` is the directory name, stamped on after the task was built.
