# Platform Defaults

Enforcing DAG-level standards across a repository: the settings authors choose from, and the
settings they never see.

## Why you'd do this

Blueprints standardise what happens *inside* a step. This example standardises everything
around it — retries, timeouts, ownership, tags, alerting.

Left to convention these values drift: one DAG has 10 retries left over from a debugging
session, another has none, and untagged DAGs have no recorded owner when they fail. Rather than
asking authors for each value, derive them from two fields they can answer reliably — who owns
the DAG, and how important it is.

## Files

| File | What it does |
|---|---|
| `dags/dag_args.py` | `BlueprintDagArgs` turning `team` + `tier` into DAG settings |
| `dags/loader.py` | `on_dag_built` applying settings authors never touch |
| `dags/payments_ledger.dag.yaml` | Critical tier |
| `dags/growth_sandbox.dag.yaml` | Experimental tier, same fields, very different DAG |
| `dags/blueprints.py` | Ordinary extract/load — not the point of this example |

```bash
../run.sh platform-defaults
```

## Walk-through

### Layer 1: the fields authors may set

A `BlueprintDagArgs` subclass works like a blueprint, but for the top level of a DAG YAML. Its
config model *is* the list of permitted top-level fields:

```python
class ProjectDagArgsConfig(BaseModel):
    schedule: str | None = None
    description: str | None = None
    team: str = Field(pattern=r"^[a-z][a-z0-9-]*$", ...)
    tier: Literal["critical", "standard", "experimental"] = "standard"
```

There is no escape hatch here. `retries` is not a field, so no YAML can set it — unlike a
defaults dict, which authors can always override locally. If a setting should not vary, leave
it out of the config.

Note `team` has no default, which makes it required. That single line is how you guarantee
every DAG in the repository is attributable:

```
FAIL noteam.dag.yaml
  Error: 1 validation error for ProjectDagArgsConfig
team
  Field required [type=missing, input_value={'schedule': '@daily'},
input_type=dict]
```

`render()` then maps those fields onto real DAG kwargs:

```python
def render(self, config: ProjectDagArgsConfig) -> dict[str, Any]:
    policy = TIER_POLICY[config.tier]
    return {
        "catchup": False,
        "max_active_runs": 1,
        "tags": [f"team:{config.team}", f"tier:{config.tier}"],
        "dagrun_timeout": timedelta(hours=policy["timeout_hours"]),
        "default_args": {
            "owner": config.team,
            "retries": policy["retries"],
            "email_on_failure": config.tier == "critical",
        },
        ...
    }
```

`catchup=False` and `max_active_runs=1` are unconditional — the house style, applied whether or
not anyone remembers it. Everything else follows from `tier`, so changing the retry policy for
every critical DAG in the company is a one-line edit to `TIER_POLICY`.

Only pass through what was actually set. Writing `"schedule": config.schedule` unconditionally
would push `None` into every DAG that omitted it, which is not the same as leaving it alone.

At most one `BlueprintDagArgs` may exist per project; a second raises `MultipleDagArgsError`.
With none defined, the built-in `DefaultDagArgs` allows just `schedule` and `description`.

### Layer 2: the settings authors never see

`on_dag_built` runs once per DAG after every step is wired, and receives the DAG and the path
it came from:

```python
def apply_platform_policy(dag: DAG, config_path: Path) -> None:
    source = config_path.name.removesuffix(".dag.yaml")
    dag.tags = [*(dag.tags or []), f"source:{source}"]

    owner = (dag.default_args or {}).get("owner", "unknown")
    dag.doc_md = (
        f"Generated by Blueprint from `{config_path.name}`.\n\n"
        f"Owner: **{owner}**. Raise issues with that team.\n"
    )


build_all_airflow_dags(on_dag_built=apply_platform_policy)
```

This is the layer for things that are not authoring decisions at all: provenance, generated
documentation, access control lists, lineage registration, pushing an inventory of DAGs to a
catalogue. It has the whole DAG object, so it can inspect what was built rather than just
what was declared.

### Which layer does a setting belong in?

Ask whether a DAG author would ever legitimately want it different.

- **Yes, within limits** → a config field, constrained. `tier` is the example: three values,
  each with a defined meaning.
- **No** → `render()`, unconditionally. `catchup=False` is not a matter of opinion.
- **Not their concern at all** → `on_dag_built`. Provenance tags and access control are platform
  bookkeeping.

The mistake to avoid is a passthrough field — accepting `retries` and forwarding it. That is
the defaults dict again, with extra steps.

## What to look at in the UI

Both DAGs, side by side in the list view, tagged `team:…`, `tier:…` and `source:…`. None of
those tags appear in either YAML file.

Open `payments_ledger` → any task → **Details**: 5 retries, a 2-hour DAG timeout, email on
failure. The same view on `growth_sandbox`: no retries, 12-hour timeout, no email. The two YAML
files differ by one word.

The **Docs** panel on each DAG is the `doc_md` from `on_dag_built`.
